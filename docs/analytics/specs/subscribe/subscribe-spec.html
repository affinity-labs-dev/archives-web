Questions This Flow Answers

Strategic Questions

  1. How many users see the subscribe paywall each day?
  2. How many users complete a purchase after seeing the paywall?
  3. How many users cancel the purchase flow after starting it?
  4. How many users use the restore purchases feature?
  5. How many users encounter a purchase error?

Behavioral Insights

  1. How many users reach the paywall from the Subscribe tab?
  2. How many users reach the paywall from a locked era?
  3. How many users reach the paywall from the daily story rewind?
  4. How many users reach the paywall from the AI quiz explanation?
  5. How many users reach the paywall from Chat to Learn on quiz results?
  6. How many non-subscribers are blocked from accessing past daily stories?
  7. How many users who are blocked from daily story rewind go on to purchase?
  8. How many users restore purchases successfully?
  9. How many users attempt restore but fail?
  10. How many users purchase a monthly plan?
  11. How many users purchase a yearly plan?
  12. How many users start a free trial?

Checkpoint Validation

  1. Subscribe Tab: Do users who open the subscribe tab actually see the paywall?
  2. Paywall Presented: Does the paywall load successfully for every entry point?
  3. Purchase Completed: Does every successful purchase result in an active subscription?
  4. Subscriber Active: Are person properties updated correctly after purchase or restore?

Analysis Notes

Dual purchase event system: subscribe_purchase_completed fires from the RevenueCat Paywall UI callbacks (all entry points), while subscription_purchased fires from useRevenueCat.purchase() only when the hook’s purchase() function is called directly. The imperative paywall (modal) entry points (daily story rewind, locked era, AI quiz, chat to learn) only fire subscribe_purchase_completed, not subscription_purchased. The Subscribe Tab fires both because it uses the embedded RevenueCatUI.Paywall component AND the useRevenueCat hook’s listener updates syncSubscriptionToPostHog.
Onboarding paywall gap: The onboarding paywall screen (onboarding-step-13.tsx) currently has zero analytics events. It marks the paywall as “seen” in AsyncStorage via PaywallGateService but does not track screen views or CTA taps. The “SEE MY FREE OFFER” button routes directly to /(tabs)/today without presenting the RevenueCat paywall, suggesting this screen is a soft-sell placeholder, not a live purchase flow.
Plan selection blindspot: The RevenueCat Paywall UI handles plan rendering and selection internally. There is no PostHog event when a user views available plans or selects one. We only learn which plan was purchased after the fact from subscribe_purchase_completed. Users who browse plans but do not tap “Subscribe” are invisible.
Missing subscription_activated event: No single event fires at the moment a user transitions from non-subscriber to subscriber. Person properties are updated via $set, but there is no dedicated event for funnel analysis of the activation moment. subscribe_purchase_completed and subscribe_restore_success serve as proxies but do not capture upgrades from external sources (promo codes, web billing, family sharing).
Founding Member detection: The app detects founding members by checking for the Archives_Lifetime_Offer product identifier on the Access of All Eras - Yearly entitlement. These users see a special thank-you screen instead of the paywall. There is no analytics event tracking founding member screen views.
